# Figma 操作识别方法说明

本文档描述 `trajfeat.py`（调用类别）和 `design_ops.py`（Figma 操作）中的识别规则。文中的每条规则都与代码一致；修改代码时请同步修改本文档。

---

## 1. 输入与范围

**数据来源。** 每条运行的轨迹文件（`trajectory*.jsonl`）中，模型发出的每一次工具调用都带有工具名和参数。只统计产出被评分文件的那些尝试，与成本口径一致。

**模型可用的工具。** 两批数据中，模型只能调用 4 个 Figma MCP 工具：

| 工具 | 作用 |
|---|---|
| `whoami` | 确认当前账号 |
| `get_metadata` | 读取文件、页面或节点的结构（只读） |
| `get_screenshot` | 渲染某个节点的截图（只读） |
| `use_figma` | 在文件中执行任意一段 Figma Plugin API JavaScript 代码 |

`use_figma` 占全部调用的约 80%，读、写、改、连线都通过它完成，所以识别的核心是**分析 `use_figma` 参数里的代码**。

**两层识别。**

- **第一层：调用类别。** 每次调用归入且只归入一类，用于统计"模型在做什么"、时间和上下文花在哪。见第 2 节。
- **第二层：Figma 操作。** 在写操作的代码里统计用到了哪些 Plugin API 操作，用于刻画"用什么方式做设计"。见第 3 节。

**识别方法。** 两层都是对代码文本做正则匹配，不执行代码，也不读取最终文件。

---

## 2. 第一层：调用类别（8 类）

### 2.1 类别定义

| 类别 | 中文 | 含义 |
|---|---|---|
| `setup` | 环境确认 | 调用 `whoami` |
| `inspect` | 读取文件状态 | 只读：读结构、读组件、读文字、核对结果 |
| `construct` | 构建 | 代码中创建了新节点 |
| `modify` | 修改 | 不创建新节点，只修改或删除已有节点 |
| `prototype` | 原型连线 | 不创建新节点，设置原型交互 |
| `verify` | 截图检查 | 调用 `get_screenshot` |
| `other_tool` | 其他工具 | 不属于上述工具的调用（主要是模型拼错的工具名，共 3 次） |
| `unknown` | 无法判断 | 代码被省略且描述中没有可用关键词 |

### 2.2 判定顺序

按以下顺序逐条检查，**命中第一条即停止**：

1. 工具是 `whoami` → `setup`
2. 工具是 `get_screenshot` → `verify`
3. 工具是其他只读工具（`get_metadata`、`get_design_context`、`get_variable_defs` 等）→ `inspect`
4. 工具是 `use_figma`：
   1. 代码为空，或被评测框架替换成了省略注释 → 按描述关键词判断（见 2.4）
   2. 代码中有**创建节点**的写法 → `construct`
   3. 否则，代码中有**设置原型交互**的写法 → `prototype`
   4. 否则，代码中有**删除节点**或**修改节点属性**的写法 → `modify`
   5. 都没有 → `inspect`
5. 其他工具 → `other_tool`

**优先级的含义：** 一次调用常常同时做几件事（例如建完一屏顺手连线）。按"构建 > 原型 > 修改 > 读取"的顺序只取一个类别，所以**"原型"和"修改"两类是下界**，有一部分被计入了"构建"。

### 2.3 判定规则

**创建节点**（命中任一即为 `construct`）：

```
figma\.create[A-Z]\w*\s*\(          # figma.createFrame / createText / createRectangle / createComponent …
\.createInstance\s*\(               # 由组件生成实例
\.clone\s*\(                        # 复制节点
createNodeFromSvg                   # 由 SVG 生成节点
importComponent\w*\s*\(             # 导入库组件
figma\.(union|subtract|group|flatten|combineAsVariants)\s*\(   # 布尔运算、编组、合并变体
```

**设置原型交互**（命中任一即为 `prototype`）：

```
setReactionsAsync                   # 设置交互
\.reactions\s*=[^=]                 # 直接赋值交互
flowStartingPoints                  # 设置流程起点
```

**删除节点**：

```
\.remove\s*\(\s*\)
```

**修改节点属性**（命中任一即为 `modify`）：

```
\.appendChild\s*\(   \.insertChild\s*\(            # 移动节点到容器
\.resize\w*\s*\(     \.rescale\s*\(                # 改尺寸
\.setProperties\s*\( \.swapComponent\s*\(          # 改实例属性、换组件
set(?!CurrentPage)\w+Async\s*\(                    # 异步设置，如 setTextStyleIdAsync；排除切换页面
\.setBoundVariable\s*\(                            # 绑定变量
<对象>.<属性> = <值>                                # 对以下属性赋值：
    x  y  name  characters  fills  strokes  effects  opacity  visible
    fontSize  fontName  lineHeight  letterSpacing  textAlignHorizontal  textAutoResize
    layoutMode  layoutSizingHorizontal  layoutSizingVertical  layoutAlign  layoutGrow
    itemSpacing  paddingLeft  paddingRight  paddingTop  paddingBottom
    primaryAxisAlignItems  counterAxisAlignItems
    cornerRadius  clipsContent  rotation  strokeWeight  constraints
```

`setCurrentPageAsync`（切换当前页面）被明确排除，因为读取另一页之前也必须调用它。第一版没有排除，导致大量读取被误判为修改，已修正。

### 2.4 代码被省略时的处理

评测框架为压缩上下文，会把部分历史调用的代码替换成注释"历史已执行脚本已省略……"。这影响约 1–7% 的代码调用，Qwen 3.8 Max（5.8%）和 Kimi K3（7.0%）最多，旧包没有这种情况。

这类调用改用模型为调用写的 `description` 判断，按以下顺序匹配英文关键词（不区分大小写），命中第一类即停止：

| 顺序 | 类别 | 关键词 |
|---|---|---|
| 1 | `prototype` | wire, wiring, link, prototyp-, reaction, interaction, navigation, hotspot |
| 2 | `construct` | build, create, add, make, draw, construct, generate, clone, instantiate |
| 3 | `modify` | fix, adjust, update, remove, delete, recolor, align, center, resize, rename, move, tweak, polish, refine, correct, repair, replace, clean, hide, swap, patch |
| 4 | `inspect` | inspect, read, list, dump, check, verify, get, find, map, audit, scan, examine, count, extract, probe, test, confirm |

都不命中则为 `unknown`。

## 3. 第二层：Figma 操作（13 类）

### 3.1 统计范围

- 只统计第一层判为 `construct`、`modify`、`prototype` 的 `use_figma` 调用（下称"写调用"）。
- 代码被省略的写调用不参与统计。
- **计数是对代码文本的出现次数。** 例如一次调用里写了 3 处 `figma.createText(`，记 3 次。

### 3.2 操作定义

| 操作 | 中文 | 匹配的 Plugin API | 规则 |
|---|---|---|---|
| `instance` | 实例化组件 | `component.createInstance()`、`figma.importComponentByKeyAsync()`、`importComponentSetByKeyAsync()` | `\.createInstance\s*\(` 或 `importComponent(?:Set)?ByKeyAsync\s*\(` |
| `own_component` | 自建组件 | `figma.createComponent()`、`createComponentFromNode()`、`figma.combineAsVariants()` | `figma\.createComponent(?:FromNode)?\s*\(` 或 `combineAsVariants\s*\(` |
| `clone` | 复制节点 | `node.clone()` | `\.clone\s*\(\s*\)` |
| `frame` | 新建容器 | `figma.createFrame()`、`createAutoLayout()`、`createSection()` | `figma\.create(?:Frame\|AutoLayout\|Section)\s*\(` |
| `primitive` | 基础图形 / SVG | `figma.createRectangle / Ellipse / Line / Vector / Polygon / Star()`、`figma.createNodeFromSvg()` | `figma\.create(?:Rectangle\|Ellipse\|Line\|Vector\|Polygon\|Star)\s*\(` 或 `createNodeFromSvg\s*\(` |
| `text` | 新建文字图层 | `figma.createText()` | `figma\.createText\s*\(` |
| `group` | 编组 / 布尔运算 | `figma.group / union / subtract / flatten()` | `figma\.(?:group\|union\|subtract\|flatten)\s*\(` |
| `autolayout` | 设置自动布局 | 给 `layoutMode` 赋值，且值不是字面量 `"NONE"` | `layoutMode\s*=(?!=)\s*(?!["'\`]NONE)` |
| `naming` | 命名图层 | 给 `.name` 赋值 | `\.name\s*=(?!=)` |
| `instance_override` | 覆盖实例 | `instance.setProperties()`、`swapComponent()`、给 `mainComponent` 赋值 | `\.setProperties\s*\(` 或 `\.swapComponent\s*\(` 或 `\.mainComponent\s*=(?!=)` |
| `style_or_variable` | 使用样式 / 变量 | `setBoundVariable`、`textStyleId` / `fillStyleId` / `strokeStyleId` / `effectStyleId` 及其 `set…StyleIdAsync` | `setBoundVariable\|(?:text\|fill\|stroke\|effect)StyleId\|set(?:Text\|Fill\|Stroke\|Effect)StyleIdAsync` |
| `image` | 使用图片 | 图片填充 `{type: "IMAGE", imageHash: …}`、`figma.createImage()` | `["'\`]IMAGE["'\`]\|imageHash\|createImage` |
| `text_edit` | 设置文字内容 | 给 `.characters` 赋值 | `\.characters\s*=(?!=)` |

`(?!=)` 用于排除比较运算 `==` 和 `===`，例如 `n.name === "Header"` 不计入命名。

### 3.3 创建类操作

以下 6 类会产生新节点，合称**创建操作**，是第 4 节比例的分母：

`instance`、`own_component`、`clone`、`frame`、`primitive`、`text`

`group` 不计入创建操作，因为编组只是把已有节点放进新的父节点，而且全部数据里只出现 5 次。

### 3.4 各操作的已知局限

| 操作 | 局限 |
|---|---|
| `instance` | 无法区分实例化的是**题目提供的组件**还是**模型自己建的组件**，两者都是 `createInstance()`。 |
| `clone` | 混合了两种用途：复制布局（如 gpt-6-astra 把页脚复制到每页）和搬运素材（如 DeepSeek 复制图片节点）。代码层面无法区分。 |
| `naming` | 对任何对象的 `.name` 赋值都会计入，包括模型为了返回结果而构造的普通对象。 |
| `autolayout` | 只识别赋值写法。如果写成对象字面量（如 `{layoutMode: "VERTICAL"}` 再传给辅助函数）则漏计。 |
| `text_edit` | 既包括修改组件实例里的文字，也包括给刚建的文字图层写内容，两者不区分。 |
| 全部 | 见第 6 节"静态计数"。 |

## 4. 派生指标

在每条运行内，把所有写调用的操作计数相加，再计算以下指标。分母为 0 时记为缺失。

| 指标 | 中文 | 定义 |
|---|---|---|
| `instance_share` | 实例化占比 | instance ÷ 创建操作总数 |
| `frame_share` | 新建容器占比 | frame ÷ 创建操作总数 |
| `primitive_share` | 基础图形占比 | primitive ÷ 创建操作总数 |
| `text_share` | 新建文字占比 | text ÷ 创建操作总数 |
| `clone_ratio` | 复制占比 | clone ÷ 创建操作总数 |
| `reuse_ratio` | 组件复用比例 | instance ÷ (instance + primitive + frame)，即"复用组件"相对"手工搭建"的比例 |
| `own_components` | 是否自建组件 | 本次运行中 own_component > 0 记 1，否则记 0 |
| `autolayout_ratio` | 自动布局密度 | autolayout ÷ frame，即平均每个新建容器设置几次自动布局；可以大于 1 |
| `naming_ratio` | 命名密度 | naming ÷ 创建操作总数；可以大于 1 |

**稳健性版本。** 每类操作另算一个"含该操作的写调用占比"（`has_<操作>`）：只看每次写调用里有没有这个操作，不看出现几次。用于检验结论是否依赖计数方式。

## 5. 校验

**第一层：与描述分类对照。** `use_figma` 要求模型为每次调用写一句 `description`。对描述只命中一类关键词的 6,239 次调用，比较按代码判定的类别与按描述判定的类别：

| 描述判为 ↓ / 代码判为 → | 读取 | 构建 | 修改 | 原型 |
|---|---|---|---|---|
| 读取 | **91%** | 3% | 5% | 1% |
| 构建 | 1% | **98%** | 1% | 0% |
| 修改 | 2% | 28% | **69%** | 0% |
| 原型 | 5% | 22% | 1% | **72%** |

总一致率 **90.5%**。主要分歧是描述为"修改"或"连线"、但代码里也创建了节点的调用，按 2.2 的优先级被判为"构建"。这与"修改、原型两类是下界"一致。

**第二层：人工抽查。** 每类操作随机抽 6 个匹配，连同前后约 120 个字符的代码上下文人工核对，13 类共 78 个匹配全部是对应的真实操作。这只检验了**精确率**（匹配到的是否正确）；**召回率**（有没有漏掉）没有系统评估，已知的漏计情形见 3.4 和第 6 节。

复现抽查：`.venv/bin/python design_ops.py out validate`

## 6. 总体局限

1. **静态计数，不是节点数。** 模型常把创建封装进辅助函数，例如定义一次 `function T(...) { figma.createText() }` 再调用 50 次，或在循环里创建。代码里只出现一次，节点却有很多个。因此第二层指标描述的是**用什么方法构建**，不是**造了多少节点**。不同模型封装程度不同，绝对数量不能跨模型比较；比例指标受影响较小，但没有完全消除。
2. **不执行代码。** 代码里写了某个操作，不代表它执行成功；失败的调用（约占 7–27%）同样被计入。
3. **不读最终文件。** 节点的真实数量、层级、是否被后续删除，需要最终文件的图层快照（"产物层"），本方法不覆盖。
4. **调用类别是单选。** 多用途调用按优先级归入一类（见 2.2）。

## 8. 产物层：最终文件的图层快照

过程层看代码，产物层看评分时的最终文件。数据是每条运行被评分那一版文件的 `benchmark-layers.json`：

- 这一批：`distributed-246-layers-only/layers-only/`，按 `score.json` 中的 `candidate.revision` 选取对应版本；212 条已评分运行全部对上。
- 旧包：每条运行目录下的 `benchmark-layers.json`，177 条中 175 条有。

**快照字段（每个产品画板一条）：** `nodes` 节点数、`max_depth` 最大嵌套深度、`instances` 实例数、`texts` 文字图层数、`images` 图片数、`types` 数量最多的前 6 种节点类型、`names` 前 6 个图层名。`types` 和 `names` 是截断的；实测前 6 种类型覆盖了几乎全部节点（中位 100%）。

**两批快照的统计规则不同。** 这一批不展开组件实例内部（实例记为 1 个节点），旧包展开。证据：旧包 58% 的画板图层名中出现状态栏实例内部的"9:41"，这一批只有 3%；这一批 43% 的画板满足"节点数 ≈ 实例数 + 文字数"，旧包只有 2%。因此**节点数、深度、类型构成只能在批内比较**，跨批分析时每个"模型 × 批次"单独取平均。

**裁判看到的就是这份快照。** 评分提示词规定 G1（命名）和 G2（图层结构）只依据图层结构摘要判断，所以快照字段与 G1/G2 的关系只作为一致性检查，不作为证据。

**每条运行的指标（先按画板计算，再取运行内中位数；节点数为 0 的空画板单独计数）：**

| 指标 | 定义 |
|---|---|
| `nodes_per_screen` | 每屏节点数 |
| `max_depth` | 每屏最大嵌套深度 |
| `instances_per_screen` / `texts_per_screen` / `images_per_screen` | 每屏实例 / 文字 / 图片数 |
| `instance_node_share` | 实例数 ÷ 节点数（运行内求和后相除） |
| `text_node_share` | 文字数 ÷ 节点数 |
| `frame_share_lb` 等 | 某类型节点数 ÷ 节点数；因类型列表截断，是下界 |
| `default_name_share` | 前 6 个图层名中默认名（如 `Frame 12`、`Rectangle`）的比例 |

代码：`product_layer.py`；事先写定的假设见 `design_ops_hypotheses.md` 第二部分。
